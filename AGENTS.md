# Instructions for coding agents

Tessera is a fork of [Folia](https://github.com/PaperMC/Folia) kept as patch files. This file is for automated
coding agents (and the people driving them). The human-facing rules are in [CONTRIBUTING.md](CONTRIBUTING.md); everything
there applies to agents too. Read both before changing anything.

## Repository map

| Path | What it is |
|------|------------|
| `folia-server/minecraft-patches/features/*.patch` | Patches to Minecraft sources (Folia's, then Tessera's) |
| `folia-server/paper-patches/features/*.patch` | Patches to Paper server sources |
| `folia-api/paper-patches/features/*.patch` | Patches to Paper API |
| `folia-server/src/minecraft/java`, `paper-server`, `paper-api` | Generated by `applyAllPatches`, git-ignored, each a **separate git repository** |
| [PATCHES.md](PATCHES.md) | One row per Tessera patch |
| [BACKLOG.md](BACKLOG.md) | Open tasks (`T-NNN`) and the "Done" table |
| [PLUGINS.md](PLUGINS.md) | Third-party plugins checked on Tessera |
| [COMPAT.md](COMPAT.md) | Design of compatibility mode for plugins without Folia support |
| [REGION_LOGIC.md](REGION_LOGIC.md) | How regions and their threads work |
| `tools/` | Test harness: `testserver.sh`, `joinbot.py`, `rcon.py` |
| `site/` | Project website (GitHub Pages) |

Never edit `.patch` files by hand and never commit the generated source directories.

## Workflow

1. `./gradlew applyAllPatches` once (it decompiles Minecraft; takes several minutes).
2. Edit sources in the nested repository and commit there. One commit = one patch = one logical change. The commit
   message becomes the patch header (format in CONTRIBUTING.md).
3. Rebuild patch files from the root. Run each rebuild task as a **separate** Gradle invocation; combining them in one
   command can leave patches half rebuilt:

   ```bash
   ./gradlew rebuildMinecraftPatches     # after commits in folia-server/src/minecraft/java
   ./gradlew rebuildPaperServerPatches   # after commits in paper-server
   ./gradlew rebuildServerPatches
   ./gradlew rebuildPaperPatches         # after commits in paper-api
   ```

   `./rb.sh` runs all of them one after another. Afterwards `git status` must show only the patch files you meant to change.
4. Build: `./gradlew createPaperclipJar` (separate invocation). The jar is `folia-server/build/libs/*-paperclip-*.jar`.
   For a quick compile check: `./gradlew :folia-server:compileJava`.
5. Test on a running server (below), then add a row to PATCHES.md and move the task in BACKLOG.md to "Done".

Builds and servers take minutes: run them in the background or with a long timeout, not with a short foreground one.

## Code rules

- Mark changed upstream lines with `// Tessera - <why>`, blocks with `// Tessera start - <why>` / `// Tessera end - <why>`
  (the same text on both).
- Change as few upstream lines as possible. Prefer a small check at the right place over a rewrite.
- Vanilla behaviour by default; gameplay changes go behind a config option that is off.
- Thread ownership: world, chunk and entity state is touched only on the thread that owns the region
  (`TickThread.isTickThreadFor(...)`). Hand work over with the region, entity or global schedulers; do not add locks
  around region state.
- New API goes into its own patch in `folia-api/paper-patches`; do not change existing public API behaviour.
- Comments and docs in English. Match the style of the surrounding code.

## Testing a change

Reproduce the problem on the current build first, then show it is gone on the new one. A change that was only compiled
is not tested.

```bash
export TESSERA_JAVA=/path/to/jdk-25/bin/java TESSERA_TEST_PORT=25600
tools/testserver.sh start /tmp/ts            # creates the server dir, copies the latest built jar, waits for "Done"
tools/testserver.sh bot /tmp/ts Bot1 60      # a player joins (tools/joinbot.py, protocol 26.3) and stays 60 s
tools/testserver.sh rcon /tmp/ts "tp Bot1 5000 -60 5000" "tessera compat"
tools/testserver.sh errors /tmp/ts           # exit 1 if the log has ERROR or exceptions
tools/testserver.sh stop /tmp/ts
```

- Keep server directories outside the repository.
- Bots far apart (for example 0,0 and 5000,5000) are in different regions. With the default `threaded-regions.threads: -1`
  a small machine runs all regions on one thread; set `threads` in `config/paper-global.yml` when the test needs
  regions ticking in parallel.
- Behaviour behind the Bukkit API is easiest to drive with a tiny test plugin (`folia-supported: true`), compiled with
  `javac -cp "$(find <server dir>/libraries -name '*.jar' | tr '
' ':')"` (`;` on Windows) and dropped into
  `<dir>/plugins`. Log with a fixed prefix and grep for it.
- `joinbot.py` has no physics and no rendering. Things that need a real client (map rendering, end credits, client-side
  velocity) must say so in the PR instead of claiming they were tested.
- The log of the final run must have no new `ERROR` or exception.

## Pull requests from agents

Agent-written pull requests are welcome under the same rules as any other. In the PR description:

- what was broken and how you reproduced it on the current build;
- what the patch changes, in a few sentences;
- the test you ran on the new build and its result (log lines, `/tessera compat` output, spark profile for performance);
- what you could not test.

One problem per PR. Do not reformat or "clean up" unrelated code, do not bump dependencies, do not touch the upstream
patches before the Tessera ones. Do not open PRs that were not built and run.

## Things not to do

- Do not push to `main`, create tags or releases; the release workflow publishes every push to `main`.
- Do not report exploits (dupes, crash exploits, permission bypasses) in issues or PRs; see [SECURITY.md](SECURITY.md).
- Do not paste private server names, addresses or logs with player data into the repository, issues or PRs.
